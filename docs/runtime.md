# The runtime kernel (M0)

The Python project [`xaikg-pipeline`](../xaikg-pipeline/) is the **model-independent kernel** of the architecture: its runtime components (LLM client, extractor, graph loader, explanation runtime) never read the M1 models; they execute generated artifacts only. Everything that depends on the models (prompts, validator, loader, explanation contract, router, templates) is generated by [`xaikg-mde`](../xaikg-mde/) and only *executed* here. Two auxiliary tools outside the generated pipeline read one model directly: **predictor training** takes the feature list from `AIModelSpec.featureNames` of the decision-bindings model, so that the predictor and the explanation contract cannot drift apart, and **corpus acquisition** takes the drug and condition names from the same model (document acquisition lies outside the framework, paper Section 4.5). Experiment E3 also edits *copies* of the policy model to create its variants. The kernel calls the Java runtime through [`mde_bridge.py`](../xaikg-pipeline/xaikg/mde_bridge.py): one JSON report on standard output per command, exit code 2 when a blocking invariant fails.

## Span location

For every entity *mention* and relation *evidence* returned for a chunk, `_locate()` in [`extractor.py`](../xaikg-pipeline/xaikg/llm/extractor.py):

1. keeps the LLM's character offsets if the chunk text at those offsets equals the quotation (case-insensitive), converting them to document offsets;
2. otherwise searches for the quotation in the chunk with an **exact, case-insensitive substring search**, starting after the previous entity to respect reading order, and records its real position;
3. if the quotation does not occur in the chunk, keeps the reported offsets: nothing is decided at this step.

The decision belongs to the generated validator: the grounding rules check that the source text at the recorded position equals the quotation ([transformations.md](transformations.md#t2-validation-as-a-higher-order-transformation)). In the case study the LLM's offsets were wrong for 99.7% of the items, whose quotations had to be searched for in the source ([kg-construction.md](kg-construction.md)).

## The LLM response cache

Every LLM response is stored in [`datasets/cache/llm/`](../datasets/cache/llm/), keyed by provider, model, prompt and chunk. With the cache, every step after extraction is deterministic and can be re-run without an API key ([reproduce.md](reproduce.md)). The cache serves reproducibility of the experiments; it is not part of the framework.

## Phase 5: the explanation service

[`generated/service/`](../generated/service/) is a FastAPI application generated by T6: [`router.py`](../generated/service/router.py) has one endpoint per pair of explanation type and audience, and [`contract.json`](../generated/service/contract.json), [`bindings.json`](../generated/service/bindings.json), [`patterns.json`](../generated/service/patterns.json) and the templates carry the explanation contract. Besides the explanation endpoints, the router exposes `/contract`, which returns the explanation contract as data, and an endpoint that returns the full provenance of a logged explanation from its identifier (R8). Evidence that does not fit the audience budget is reported as *omitted*, and a factor without validated evidence is reported as *none*; nothing is invented. Run it with `make serve` (Neo4j must be running); example inputs are in [`generated/service/examples/`](../generated/service/examples/).

## The explanation log

Every delivered explanation is appended to [`results/explanations/explanations.jsonl`](../results/explanations/explanations.jsonl) with its decision, audience, explanation type, text, facts (fact identifiers with source and span) and the fingerprints of the models behind the service (`service_models`). The committed log contains the 1,574 explanations of the final evaluation run ([E4](experiments.md#e4--traceability-of-the-delivered-explanations)).
